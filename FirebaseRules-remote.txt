Mayflower Radio — remote control rules
======================================

Paste these five nodes into the Realtime Database rules, alongside the rules you
already have for "stations", "likes" and "requests". Keep everything else as it
is; this only adds nodes, it doesn't change any existing one.

Firebase console → Realtime Database → Rules → paste inside the top-level
"rules" object → Publish.

Until these exist, remote control does nothing at all: every read and write
comes back 401, which from the outside looks exactly like "nobody has pressed
anything". The app says so out loud rather than sitting there quietly.


    "radioOwner": {
      "$sid": {
        ".read": true,
        ".write": "!data.exists() || (auth != null && auth.uid === data.child('uid').val())",
        ".validate": "newData.hasChild('uid')"
      }
    },

    "radioNow": {
      "$sid": {
        ".read": true,
        ".write": true
      }
    },

    "radioHome": {
      "$sid": {
        ".read": "auth != null && (auth.uid === root.child('radioOwner').child($sid).child('uid').val() || root.child('radioFriends').child($sid).child(auth.uid).exists())",
        ".write": true
      }
    },

    "radioControl": {
      "$sid": {
        ".read": true,
        "$cmd": {
          ".write": "!newData.exists() || (auth != null && newData.child('by').val() === auth.uid && (auth.uid === root.child('radioOwner').child($sid).child('uid').val() || (root.child('friends').child(root.child('radioOwner').child($sid).child('uid').val()).child(auth.uid).exists() && newData.child('cmd').val() !== 'stop' && newData.child('cmd').val() !== 'start')))",
          ".validate": "newData.hasChildren(['cmd','by','at']) && newData.child('cmd').isString() && newData.child('cmd').val().length < 20 && newData.child('arg').val().length < 300"
        }
      }
    },


Why each one is shaped like that
--------------------------------

radioOwner — who a station belongs to. Writable while nobody owns it, which is
how the app claims it the first time you sign in. After that only the signed-in
owner can change or clear it. A station can't be quietly taken over.

Friends — there is no radio-specific friends list. A station uses the site's
existing one at /friends/<owner>/<visitor>, the same one account.html manages
with requests and accepting. Your friends are your station's friends, there's
only one list to keep straight, and unfriending someone takes their controls
away in the same moment.

radioNow — what's playing, for the page to show. Public on purpose, and it
carries no address: the station id is enough to see a track list, and that's
all this holds.

radioHome — the station's actual address, which contains the owner's home IP.
Readable only by the owner and their approved friends. That's the one node here
where the read rule really matters.

radioControl — the commands themselves, and the important one. A command is
only accepted if the writer is signed in, stamps it with their own uid, and is
either the owner or an approved friend. "stop" and "start" are refused for
friends, so only you can take your station off air. Reads and deletes are open
because the app consumes these without signing in.


The honest limits
-----------------

The app talks to Firebase without credentials — it has no account of its own —
so anything the app writes is a node the database has to leave writable:
radioNow, radioHome, and deleting from radioControl. Someone who knew a station
id could therefore write junk into what the page displays, or delete a pending
command. They could not send a command (that needs a signed-in, approved
account) and they could not read a station's address (that needs to be the owner
or a friend). The parts that matter are the parts that are locked.

Station ids are random and are only published for stations that opted into the
public directory, so for an unlisted station there's nothing to guess at.
